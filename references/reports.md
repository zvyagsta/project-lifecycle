# Reports: content, approval and release

Use this guide for a report and its visual companion for other readers. The internal review keeps detailed evidence; the external report explains the result. Audience, period, design and export formats come from the project. The user's explicit format or approval instructions take precedence.

## Content

1. **Show progress against the plan.** State the goal, what changed during the period and how the work advances that goal. Describe unfinished work through its current state and next action. Keep material delays, risks and unresolved decisions visible; positive framing must not imply completion that the evidence does not support.
2. **Explain the purpose and value of the work.** For significant actions, connect the reason for doing them, the result and its consequence. Include enough relevant background for a reader to understand the work and the effort from the report itself, without opening a chat or project context. This applies to research, coordination, preparation, implementation and other work, not only tests. Do not invent hours, savings or outcomes to justify effort.
3. **Use numbers when they help.** Include a measure only if it clarifies scale, change, an outcome or the basis for a decision. Omit counts that merely advertise activity. Keep supporting figures in internal evidence when they are needed for traceability.
4. **Take next steps from the current plan.** Summarize the nearest planned actions and their purpose, preserving their order and relation to the next expected outcome. Label the plan's period explicitly when it differs from the report period. A target date remains a plan, not a promise or a completed result.

Before presenting, read the report without its internal sources: can a reader understand why the work was needed, what changed, what the result means and what comes next? Add the missing connection instead of sending the reader to background files. Keep private evidence and source notes outside the shareable output.

## HTML first, export after approval

- Draft from evidence internally, then show the report and infographic together as designed HTML previews. Do not require the user to read and approve a separate text draft before seeing the layout.
- Check the text and visual layout before presenting. Use the project's design or the bundled templates; label previews as unapproved. If a local builder requires approved text, use an explicit preview mode or a separate preview build. Never set a false approval status to run it.
- Approval covers the presented content and layout. Export that version to the project's accepted formats only after approval. Record which version was approved; approval of an earlier version does not cover later changes in meaning.
- When the user requests a small correction to an otherwise accepted version, preserve the accepted parts and change only the requested material. Keep the prior version for rollback. An authorized mechanical correction need not reopen unrelated content for approval.
- Check exported files at their intended size and verify that the full approved text survived. Resolve clipping, missing content and font failures before delivery. Export and approval do not prove that anyone received the report.

## Links and period-folder cleanup

For user-facing links to local files, make the whole resolved absolute path visible and clickable; do not hide it behind a short label. Use the actual path on the current device. Public skill files and templates retain relative links or neutral placeholders, never a real project's path.

After a successful release, keep only the approved final-format documents, the latest approved period plan (working source and reading version where used), and the active period prompt if one exists in the main period folder. Do not create a prompt just to fill this list. Preserve the current plan during reporting; a report release is not a reason to archive the plan it still uses. If no plan is approved, keep the active plan clearly marked with its real status rather than claiming approval or making it disappear.

Move superseded versions, text drafts, HTML render sources, internal notes, duplicate exports and intermediate files into a dated archive. Never delete them or overwrite an existing archive entry. Identify the retained set before moving, check that source and destination paths stay inside the intended period folder, and verify the retained files are unchanged. Update live navigation and links within moved materials; preserve older archival snapshots. Record the new locations and check local links. Sending or publishing the final documents remains a separate action requiring authorization.
