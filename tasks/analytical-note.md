# analytical-note — research and explain a project question

**When:** the user requests an analytical note, research brief, or evidence-based explanation for a project decision.

**Input:** the exact question, audience, relevant project context, available evidence, date sensitivity, and requested output format.

**Steps**
1. State the full question, intended decision, audience, and scope. Break it into the material subquestions that could change the conclusion; keep an internal coverage list so a partial search does not silently narrow the answer. Read applicable project facts and rules. Keep personal data in the local project: use generic or anonymized search queries and do not upload source materials containing personal data to external services.
2. Research every material subquestion. Collect current primary sources when behavior may have changed, follow relevant leads beyond the first result, and reconcile conflicting evidence. Use forum discussions as examples or leads, not as proof of product behavior. Record which subquestions have evidence and which remain unresolved after a reasonable search.
3. Use the Minto pyramid by default: answer the stated question first, group the supporting reasons logically, then place mechanisms, cases, limits, and evidence beneath each reason. Make this hierarchy visible in the opening summary and headings. Follow a different structure only when the user explicitly requests one.
4. Check each conclusion and decisive claim against its source. Label published product behavior, observations in the user's environment, inferences, and unresolved questions separately. Give dates and direct links where they matter. Do not imply that published documentation proves the current installation behaves the same way.
5. Explain what changes across relevant roles or scenarios, where the answer can fail, and what narrow check would settle each material unknown. Include an implementation or test path only within the authorized scope.
6. Produce the requested format. If it is HTML, build a designed reading page that works offline, with clear hierarchy and readable type; use the project's established style when available. Check source links and internal navigation, and compare its text and conclusion with the verified draft. Preserve previous editions when revising.
7. For HTML, after the last content or style change, open and visually inspect the exact file to be delivered at wide and narrow widths (for example, 1280 and 400 px). Read through the full page; check table readability and access to every column, wrapping of long paths and URLs, navigation targets, and unwanted page overflow. A link check or automated layout pass alone is insufficient. If a tool skips rendering, use another visual method. Without this visual review, the HTML remains a draft.
8. Present the produced file with its actual status, local link, and concise conclusion; name any research or visual checks still open. Update project context and check its links when local project rules require it.

**Result:** a note that covers the question, lets a reader trace conclusions to dated evidence, and has a visually checked reading copy when delivered as HTML.

**Done when:** every material subquestion has been researched and addressed or explicitly marked unresolved, the main conclusion is supported, and the requested deliverable has passed its final-format checks. An HTML note is ready only after visual review of the final version at both widths, including tables, long paths, and navigation. If decisive research is incomplete or a visual check remains open, provide the draft with its true status and the exact remaining work; a fully researched finding of insufficient evidence can be a final conclusion.

**Do not:** send personal data outside the local project, stop research after covering only part of the question, present a forum anecdote as a confirmed rule, call an unverified draft ready, turn a proposed test into a completed one, change external systems on a research request, or publish or send the note externally without authorization.
