# analytical-note — research and explain a project question

**When:** the user requests an analytical note, research brief, or evidence-based explanation for a project decision.

**Input:** the exact question, audience, relevant project context, available evidence, date sensitivity, and requested output format.

**Steps**
1. State the question and scope. Read applicable project facts and rules; collect current primary sources when the answer may have changed. Keep personal data in the local project: use generic or anonymized search queries and do not upload source materials containing personal data to external services. Use forum discussions as examples or leads, not as proof of product behavior.
2. Use the Minto pyramid by default: answer the stated question first, group the supporting reasons logically, then place mechanisms, cases, limits, and evidence beneath each reason. Make this hierarchy visible in the opening summary and headings. Follow a different structure only when the user explicitly requests one.
3. Label source-backed product behavior, observations in the user's environment, inferences, and unresolved questions separately. Give dates and direct links for claims where the date or source matters. Do not imply that published documentation proves the current installation behaves the same way.
4. Explain what changes across relevant roles or scenarios, where the answer can fail, and what narrow check would settle each material unknown. Include an implementation or test path only within the authorized scope.
5. Produce the requested format. For an HTML reading copy, make it self-contained and usable offline; check its source links, internal navigation, text, and layout. Preserve previous editions when revising. Update project context and check its links when local project rules require it.

**Result:** a note that a reader can understand from the conclusion and trace back to dated evidence.

**Done when:** the question is answered within the evidence available, important unknowns and next checks are explicit, and the deliverable opens in the requested format.

**Do not:** send personal data outside the local project, present a forum anecdote as a confirmed rule, turn a proposed test into a completed one, change external systems on a research request, or publish or send the note without authorization.
